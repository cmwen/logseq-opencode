- ## PKCE + OIDC Cheatsheet
  - **One-line takeaway**: PKCE secures OAuth2/OIDC flows for public clients (SPAs, mobile apps) by proving the auth request and token request came from the same app—no client secret needed.
- ## What is PKCE?
  - **Proof Key for Code Exchange** (RFC 7636)
  - Security extension for OAuth 2.0 Authorization Code flow
  - **Problem it solves**: Public clients (JavaScript apps, mobile apps) can't safely store client secrets
    - Attacker could intercept authorization code and exchange it for tokens
    - PKCE prevents authorization code interception attacks
  - **Core idea**: Prove that the same client that started the auth flow is completing it
- ## Key Concepts
  - **code_verifier**
    - Random cryptographic string (43-128 chars, URL-safe)
    - Generated by client, kept secret on device
    - Think of it as a "one-time password" for this auth session
  - **code_challenge**
    - Derived from code_verifier using a hash function
    - Sent to authorization server at the start
    - Formula: `BASE64URL(SHA256(code_verifier))`
  - **code_challenge_method**
    - `S256` (SHA-256, recommended) or `plain` (not recommended)
    - Tells server how to verify the challenge
  - **Memory hook**: "Challenge first, Verify later" — send the challenge with auth request, send verifier with token request
- ## PKCE Flow (Step-by-Step)
  - **Step 1: Client generates PKCE parameters**
    - Create random `code_verifier` (e.g., 43-128 char string)
    - Hash it to create `code_challenge = BASE64URL(SHA256(code_verifier))`
    - Store `code_verifier` locally (memory/session storage)
  - **Step 2: Authorization request (to /authorize endpoint)**
    - Client redirects user to authorization server
    - Parameters: `client_id`, `redirect_uri`, `response_type=code`, `scope=openid profile email`
    - **Plus PKCE**: `code_challenge`, `code_challenge_method=S256`
    - Server stores code_challenge with the authorization code
  - **Step 3: User authenticates & consents**
    - User logs in at authorization server
    - Grants permission to client app
  - **Step 4: Authorization code returned**
    - Server redirects back to `redirect_uri` with authorization `code`
    - Example: `https://yourapp.com/callback?code=AUTH_CODE`
  - **Step 5: Token request (to /token endpoint)**
    - Client exchanges code for tokens
    - Parameters: `grant_type=authorization_code`, `code=AUTH_CODE`, `redirect_uri`, `client_id`
    - **Plus PKCE**: `code_verifier` (the original unhashed value)
    - **No client_secret required** (that's the magic!)
  - **Step 6: Server validates PKCE**
    - Server retrieves stored `code_challenge`
    - Hashes the received `code_verifier`: `SHA256(code_verifier)`
    - Compares: does it match stored `code_challenge`?
    - If match → issue tokens; if not → reject
  - **Step 7: Tokens returned**
    - **ID Token** (JWT with user identity claims: sub, email, name)
    - **Access Token** (for API calls)
    - Optional: Refresh Token
- ## PKCE with OIDC
  - OIDC = OAuth2 + Authentication layer
  - **OAuth2 alone**: Gets access tokens for AUTHORIZATION (access to resources)
  - **OIDC**: Gets ID tokens for AUTHENTICATION (user identity) + access tokens
  - **PKCE enhances both**:
    - Secures the authorization code exchange
    - Protects both ID token and access token from interception
  - **Scope**: Include `openid` to trigger OIDC behavior
    - `scope=openid profile email` → returns ID token with user claims
- ## When to Use PKCE
  - **ALWAYS use for public clients**:
    - Single Page Applications (React, Vue, Angular)
    - Mobile apps (iOS, Android)
    - Desktop apps
    - Any client that can't securely store secrets
  - **Also recommended for confidential clients** (best practice):
    - Adds extra layer of security even when client_secret is used
    - OAuth 2.1 draft makes PKCE mandatory for all clients
  - **Don't use plain passwords or implicit flow** — deprecated for security reasons
- ## Comparison: Standard vs PKCE Flow
  - **Standard Authorization Code Flow** (confidential clients)
    - Uses `client_secret` to authenticate at token endpoint
    - Secure for backend apps (server-to-server)
    - Secret must be kept safe (can't be exposed in browser/mobile)
  - **PKCE Flow** (public clients)
    - Uses `code_verifier` + `code_challenge` (dynamic, per-session)
    - No permanent secret to leak
    - Safe for browser and mobile environments
  - **Key difference**: PKCE proves same client via cryptographic proof, not static secret
- ## Visual Mnemonic
  - Think of PKCE like a **coat check ticket**:
    - You give your coat (code_challenge) at start
    - Get a claim ticket (authorization code)
    - Return with matching stub (code_verifier) to get coat back (tokens)
    - If stub doesn't match → no coat for you!
- ## Active Recall Questions
  - Q: What does PKCE stand for and what problem does it solve?
    - A: Proof Key for Code Exchange. It prevents authorization code interception attacks in public clients that can't store secrets.
  - Q: What are the two main PKCE parameters and how are they related?
    - A: code_verifier (random string) and code_challenge (SHA256 hash of verifier). Challenge is sent first, verifier is sent later to prove same client.
  - Q: When do you send code_challenge vs code_verifier in the flow?
    - A: code_challenge goes with the authorization request (/authorize). code_verifier goes with the token request (/token).
  - Q: What is the recommended code_challenge_method and why?
    - A: S256 (SHA-256 hash). It's more secure than "plain" because even if challenge is intercepted, attacker can't derive the verifier.
  - Q: What's the difference between OAuth2 and OIDC in terms of tokens?
    - A: OAuth2 returns access tokens for authorization. OIDC adds ID tokens (JWT) for authentication/user identity, built on top of OAuth2.
  - Q: Why can't SPAs use client_secret safely?
    - A: Because client_secret would be exposed in browser JavaScript code (view source, DevTools), making it not secret anymore.
- ## Flashcards (Q/A Format)
  - Q: PKCE is used for which type of clients?
    - A: Public clients (SPAs, mobile apps, any client that can't securely store secrets)
  - Q: What does code_verifier look like?
    - A: Random cryptographic string, 43-128 characters, URL-safe (A-Z, a-z, 0-9, -, _, ~)
  - Q: How do you generate code_challenge from code_verifier?
    - A: BASE64URL(SHA256(code_verifier))
  - Q: What happens if an attacker intercepts the authorization code but doesn't have code_verifier?
    - A: Token request fails because server can't verify the PKCE proof—attacker can't exchange code for tokens.
  - Q: What scope must be included to get an ID token in OIDC?
    - A: openid (plus optional profile, email, etc.)
  - Q: Is PKCE only for public clients?
    - A: No, OAuth 2.1 recommends PKCE for ALL clients (public and confidential) as best practice.
